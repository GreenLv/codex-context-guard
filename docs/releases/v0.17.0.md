# Context Guard 0.17.0 — Unreleased source candidate

Source, native, artifact, CI, HOL and public-release evidence are recorded
separately in the acceptance record and release assets.

## English

### Highlights

- Planning a change no longer creates an obligation to edit files. Another person's completed work, quoted advice, future intent and “do not modify” stay distinct from a current instruction. Requests that also ask for an actual edit retain that obligation.
- Terminal evidence recognizes the Desktop `aggregated_output` field alongside `stdout`. Conflicting output or mismatched command identity, working directory, status or exit code remains unavailable. Unrelated large transcript rows no longer hide later normal results; malformed, ambiguous or potentially relevant rows still prevent certification.
- Session retention returns as an opt-in maintenance command. Preview is the default, installation does not enable deletion, and eligible sessions enter recoverable quarantine before permanent removal. Unfinished, active, locked, legacy and unverifiable objects remain protected; SessionEnd performs no sweep.
- New installations use the stable marketplace identity `codex-context-guard`. Moving from the experimental identity can affect its old cache: finish tasks that require the published 0.16.1 runtime first, or keep them in a separately configured HOME. Cache retention alone does not prove which Hook an old task loads.

### Changes

- An enabled retention policy defaults to a 30-day minimum age and seven-day quarantine. Apply rechecks the selected objects under lifecycle and maintenance locks; interrupted quarantine, restore and purge retain recovery records. Purge waits for the grace period and leaves an expiring record that prevents silent recreation of a purged ledger.
- Independent maintenance runs keep discovery and processing progress on disk. A names-only scan must fit the invocation budget, which defaults to 20 seconds; otherwise `capacity_exceeded` and backlog remain visible, completion is not claimed, and registered work continues. Purge makes incremental progress when the budget covers its next path and deletion unit. A failed progress write returns an error instead of reporting successful maintenance.
- Scheduling is an explicit enable/status/disable operation, separate from policy adoption and installation. The verified interpreter runs the same maintenance executor through launchd or Windows Task Scheduler. Definitions, loaded state and ownership are checked separately; unrelated jobs are refused.
- The historical incident pin covers the three reproduced scope and terminal-evidence defects. A rejected intake retains its original bytes outside the active case denominator, with corrected facts under a new identity.
- Existing session data and consumed caches are not migrated. Installation creates neither a retention policy nor a scheduler. See the [stable identity contract](../../tools/validation/STABLE_MARKETPLACE_IDENTITY.md) and [session storage](../SESSION_STORAGE.md) before changing an existing HOME.
- Source candidate repairs after cross-platform review: on Windows the discovery snapshot is written with LF bytes, so the product reads back its own hints (a CRLF snapshot from an earlier candidate is treated as damaged and rebuilt), and records that discovery restores are served in the same pass. Purge now binds each quarantined object to its creation time (change time where the filesystem reports none) in addition to its file identity, so a replacement directory that reuses a freed inode is refused instead of removed. The retention acceptance batch is `cg-retention-native-batch/v4`: purge outcomes are recorded per object before any later dispatch and re-derived by the consumer.

### Validation

- Local source evidence: focused source regressions and synthetic fresh-process controls cover scope interpretation, terminal evidence, retention identity and recovery, capacity reporting and incremental purge. The macOS source suite completed 3,137 tests with zero failures or errors (94 platform/capability or historical-retirement skips). The canonical historical-library gate, performance comparison, native macOS/Windows behavior, exact-artifact installation and upgrade, CI and HOL remain separate required evidence. See [local acceptance](../LOCAL_ACCEPTANCE.md) for the current results and limits.
- Cross-platform review of the earlier candidate (`ffac148`) failed: native Windows retention batch 8/12 (CRLF snapshot self-incompatibility) and Linux CI replacement refusal on Python 3.10–3.14. Those results stay failed. The repair is macOS source evidence only: emulated Windows newline translation and forced identity reuse reproduce the failures on the earlier source and pass on the repair; native Windows, Linux CI and every downstream gate must run again on the new commit.

## 简体中文

### 亮点

- 规划修改不再产生必须编辑文件的义务。他人已完成的工作、引用的建议、未来意图和“不修改”与本轮实际指令分开处理；同时明确要求实际修改的请求仍保留该义务。
- 终端证据同时识别 Desktop 的 `aggregated_output` 和旧 `stdout` 字段。输出冲突，或命令身份、工作目录、状态、退出码不符时，仍不认证。无关的大记录不再遮蔽后续正常结果；畸形、歧义或可能包含相关结果的记录仍使证据不可用。
- 会话保留清理作为显式采用的维护命令恢复。默认只预览，安装不启用删除，合格会话先进入可恢复隔离区，再永久回收。未完成、活动、锁占用、旧版和无法验证的对象继续受保护；SessionEnd 不执行清扫。
- 新安装使用稳定市场身份 `codex-context-guard`。从实验身份切换可能影响旧缓存：请先完成依赖已发布 0.16.1 运行时的任务，或将其保留在另行配置的 HOME 中。缓存仍在不能证明旧任务实际加载了哪一个 Hook。

### 变更

- 启用保留策略后，默认要求会话结束至少 30 天，并隔离 7 天。Apply 在生命周期锁和维护锁内复核所选对象；隔离、恢复、永久回收中断时保留恢复记录。永久回收等待宽限期，并留下会到期的记录，防止同名账本被静默重建。
- 独立维护进程把发现与处理进度保存在磁盘。一次只读名字的完整扫描必须放进单次预算，默认上限仍为 20 秒；放不下时明确报告 `capacity_exceeded` 和积压，不声称完成，已登记工作继续推进。预算足够处理下一段路径与删除单元时，永久回收逐批取得进展。进度写入失败会返回错误，不再报告维护成功。
- 调度器须显式启用、查询或停用，与采用策略、安装分别进行。经验证的解释器通过 launchd 或 Windows 任务计划程序运行同一维护执行器。定义、实际启用状态和归属分别核对；不操作无关任务。
- 历史错误库固定快照覆盖本版复现的三项范围和终端证据缺陷。拒收记录保留原始字节、不计入有效案例分母，更正后的事实使用新身份。
- 不迁移既有会话数据或已消费缓存；安装既不创建保留策略，也不注册调度器。修改既有 HOME 前，请阅读[稳定身份合同](../../tools/validation/STABLE_MARKETPLACE_IDENTITY.md)和[会话存储](../SESSION_STORAGE.md)。
- 跨平台复核后的源码候选返修：Windows 上发现快照按 LF 字节写出，产品能读回自己的提示（早期候选写出的 CRLF 快照按损坏处理并重建），本轮发现补回的隔离记录在同一轮内处理。永久回收除文件身份外还绑定隔离对象的创建时间（文件系统不提供时改用变更时间），复用已释放 inode 的替换目录会被拒绝而不是删除。保留验收批次升级为 `cg-retention-native-batch/v4`：永久回收结果在任何后续调度前逐对象记录，并由消费者重新推导。

### 验证

- 本地源码证据：定向源码回归与合成新进程控制覆盖范围解释、终端证据、保留对象身份与恢复、容量报告和分批永久回收。macOS 源码套件完成 3,137 项测试，零失败、零错误（94 项因平台能力或历史退役而跳过）。完整历史库门、性能对照、macOS/Windows 原生行为、精确制品安装升级、CI 和 HOL 仍须分别取得证据。当前结果与边界见[本地验收记录](../LOCAL_ACCEPTANCE.md)。
- 早期候选（`ffac148`）的跨平台复核未通过：Windows 原生保留批次 8/12（CRLF 快照自不兼容），Linux CI 在 Python 3.10–3.14 上替换拒绝失败。这些结果保持失败。返修仅有 macOS 源码证据：模拟 Windows 换行转换与强制身份复用在早期源码上复现失败、在返修上通过；Windows 原生、Linux CI 及全部下游门须在新提交上重新运行。
