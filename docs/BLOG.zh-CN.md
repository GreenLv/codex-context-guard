# Codex长任务如何避免“压缩后忘记要求”：Context Guard开源

如果你只让Codex修改一个小函数，上下文通常不是问题。

但当任务持续几个小时甚至几天，情况就会慢慢发生变化：需要阅读大量文件、反复运行测试、等待长时间实验、协调多个Agent，还可能在中途收到新的修订和限制。随着对话越来越长，Codex会进行上下文压缩；压缩后的摘要往往还能保留“做过哪些工作”，却不一定能完整保留“最初必须满足什么”。

这类问题最麻烦的地方，不是模型完全忘记了任务，而是它只忘记了决定正确性的那一小部分：

- 最初明确禁止修改的范围；
- 后来补充的验收标准；
- 某条旧要求已经被新要求替代；
- 一个局部测试通过，并不代表整个任务已经完成；
- Subagent完成了委托工作，但它没有权限替用户改变根任务。

结果可能是：代码写了不少，测试也跑了几个，最后却对着一个已经漂移的目标宣告“完成”。

我希望解决的不是“怎样生成更长的摘要”，而是一个更具体的问题：

> 在长任务经历上下文压缩、恢复和多Agent协作之后，如何仍然保留权威需求，并且只有在存在有效证据时才能宣告完成？

为此，我整理并开源了：[Context Guard](https://github.com/GreenLv/codex-context-guard)。

它是一个面向Codex的本地正确性旁路（correctness sidecar），利用生命周期Hooks在本机维护一份私有、可校验的任务账本，并在上下文压缩后恢复最重要的任务边界。

> 项目地址：[https://github.com/GreenLv/codex-context-guard](https://github.com/GreenLv/codex-context-guard)
>
> 首个开源版本：v0.4.6

## 1. 它不是另一套“记忆系统”

Codex本身已经负责conversation、compaction、Plan mode、Goal、subagents、worktrees和memories。Context Guard没有重新实现这些功能，也不会维护第二套计划UI或Agent调度器。

它只在旁边保护四类与任务正确性直接相关的状态：

1. **权威需求与验收标准**：用户最初提出了什么，哪些事项必须满足；
2. **显式修订**：后续要求替代了什么，而不是直接把旧要求从历史中抹掉；
3. **有限工作状态与证据**：最近一次原生计划快照、工具实际返回了什么、结果是否成功；
4. **完成门禁**：当前仍有哪些未完成项，哪些成功证据足以支持完成声明。

可以把两者的关系理解为：

```text
Codex原生运行时
  对话 / 压缩 / Plan / Goal / Subagents / Worktrees / Memories
                              │
                              ▼
Context Guard正确性旁路
  不可变提示账本 → 需求与修订
  有界工具证据   → 完成门禁
  原生计划镜像   → 恢复索引
  Agent来源记录  → 有界协作状态
                              │
                    压缩前保存，压缩后恢复
```

Context Guard并不会让模型“永远记住一切”。恰恰相反，它有意只恢复与正确性最相关、且大小受限的内容。

## 2. 我比较看重的四个设计

### 2.1 需求不会被静默改写

每条提示都会在插件私有目录中形成不可变记录，并使用SHA-256绑定内容。复杂任务激活保护后，插件会为需求和验收项分配稳定ID。

如果用户后来修改要求，Context Guard记录的是一条显式supersession：新要求替代了哪条旧要求、修改发生在什么时候。旧记录仍然保留，不会因为摘要重写而消失。

对于“不要取消原要求”这类带否定的表达，或者一句话中同时出现多个可能目标的情况，插件会选择fail closed：宁可保留原要求等待确认，也不擅自判断它已经失效。

### 2.2 压缩后恢复的是任务边界，而不是完整历史

在`PreCompact`阶段，插件先校验私有状态的内容哈希，再原子地保存恢复包。`SessionStart`以compact或resume方式触发时，会按优先级恢复：

- 仍然有效的需求和验收项；
- 明确的修订关系；
- 最近一次成功的原生`update_plan`镜像；
- 正在进行和最近完成的Agent状态；
- 最近的成功、失败和未知证据；
- 完成门禁规则。

如果状态被篡改或截断，插件只允许从通过哈希验证的不可变提示记录重建。重建后的需求重新回到pending状态，因为历史证据不能在状态损坏后被静默重新信任。

### 2.3 “PASS”不等于有效完成证据

真实工具输出比想象中复杂。一个命令可能退出码为0，却在普通日志中出现`Operation not permitted`警告；也可能打印了`PASS`，随后又出现Traceback。

Context Guard会优先使用结构化状态和退出码。普通文本、弱成功标记以及含糊结果默认记为unknown，不能直接用于完成门禁；明确失败、异常和非零退出仍然是失败。

对于只能返回字符串的验证脚本，要求也很简单：任何检查不满足时必须以非零状态退出，只有全部通过后才输出精确的独立完成标记。这样“看起来像成功”和“验证过程确实成功”不会混为一谈。

此外，截图、音频或其他data URL不会整段写入证据。插件只保留数据类型、长度和哈希，避免把大量base64内容带入私有状态和恢复上下文。

### 2.4 Subagent有来源，但没有根权限

多Agent任务中，一个常见风险是把委托提示误认为用户的新要求。Context Guard会记录Agent开始和结束事件，给Subagent注入一个有界委托契约，并要求结果尽量包含：Outcome、Evidence、Validation、Limitations和Next。

但Subagent只能在委托范围内工作，不能创建、取消或替代根任务需求。插件保存的是有界结果摘要与来源信息，不读取完整Subagent transcript，也不保存隐藏推理。

## 3. 私有状态不会进入Git仓库

Context Guard的公开仓库只包含插件代码、Hooks、Schema、文档和测试。实际运行时数据写入Codex管理的`PLUGIN_DATA`，包括提示记录、需求账本、证据摘要和恢复文件。

这些内容默认只留在本机，不属于Git仓库。插件本身不发起网络请求，也没有第三方运行时依赖。

当用户显式执行`context-guard export`或`rollover`时，插件可以生成脱敏handoff或有界successor pack。导出会省略原始提示文件、transcript正文、常见凭据、认证头、URL query和插件私有路径，而且必须由用户主动触发。

需要强调的是，脱敏是防御性措施，不代表任意用户文本都一定不含敏感信息。任何准备分享或提交的handoff仍然应该人工检查。

## 4. 安装与第一次验证

项目要求Python 3.10或更高版本；当前验证的Codex CLI最低基线为`0.146.0`。

克隆仓库后运行：

```shell
git clone https://github.com/GreenLv/codex-context-guard.git
cd codex-context-guard
python3 scripts/manage_plugin.py --apply
```

Windows可以使用：

```powershell
py -3.10 scripts\manage_plugin.py --apply
```

安装器会注册仓库marketplace、安装插件并检查源码与缓存一致性。升级时，它会保留旧版本Hook缓存，因为已经运行的任务可能仍然持有旧缓存的绝对路径；如果源码改变但版本号没有变化，安装器会拒绝就地刷新。

安装完成后，还需要做两件事：

1. 启动一个新的Codex CLI任务；
2. 打开`/hooks`，检查八类Hook定义，只在确认命令与仓库一致时信任。

插件安装并不会自动信任Hook，也不建议使用trust bypass。

之后可以在全新任务中输入：

```text
$context-guard
```

再使用：

```text
context-guard status
```

如果希望验证真正的恢复链，可以创建一个包含多条要求的非简单任务，执行`/compact`，然后检查紧接着的continuation是否恢复了相同的需求边界。

## 5. 它适合哪些任务？

Context Guard更适合下面这些场景：

- 任务会持续较长时间，可能经历一次或多次上下文压缩；
- 初始要求、禁止事项和验收标准较多；
- 中途会收到新的修订，需要保留“旧要求如何被替代”的关系；
- 需要运行较多工具、测试或实验，不能把局部成功误认为整体完成；
- 使用多个Subagent，需要明确根任务与委托任务的权限边界；
- 需要把任务交接给后续执行者，但不希望复制完整会话和隐私状态。

如果只是修改几行代码、一次对话即可完成，Context Guard可能没有必要启用完整保护。它会继续保持提示记录，但只有复杂任务、Goal、显式启用或首次压缩等条件满足时，才激活完整恢复和完成门禁。

## 6. 当前边界

Context Guard能够检查“是否仍有未完成需求”和“完成声明是否绑定了成功证据”，但它不能证明一条证据在语义上真的足以满足某项需求。它也不是安全沙箱、云同步服务、完整transcript备份或第二套Agent调度系统。

当前版本在macOS上有完整的既有验证谱系，并在独立开源候选仓库中重新执行回归、安装和生命周期检查。Windows会进入跨平台CI，但在完成原生0.4.6 fresh-runtime smoke之前，只能描述为CI验证，不能直接宣称与macOS完全等价。Linux同样以CI和隔离生命周期为边界。

我希望这个项目保持克制：先把“需求不静默丢失、修订可追踪、无证据不宣告完成、私有状态不进入Git”这几件事做扎实，再根据可复现的问题决定是否继续扩展。

## 7. 总结

Context Guard的核心思路可以概括为一句话：

> 不依赖压缩后的摘要猜测任务契约，而是在本机维护一份私有、可校验的需求与证据账本，并在完成前重新核对它。

如果你也在使用Codex处理长任务，经历过压缩后要求漂移、局部测试通过却提前收尾，或者多Agent协作中权限边界不清的问题，欢迎试用：
