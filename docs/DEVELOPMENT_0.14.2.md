Renaming a suite directory from `neutral` to `audit` must not remove an
explicit request to continue until completion. The object's original text
and offsets remain available to the source and target checks. A real second
instruction such as “test the suite and review the results” remains a compound
request; one test result does not close it.

Unquoted text immediately following a filename extension in CJK can be either
part of the locator or adjacent instructions. This candidate retains the full
bytes as ambiguous and does not certify a smaller action. Quoted locators
remain explicit. Effective unit waits apply to that unit and descendants;
observed results remain observed while their waiting-condition identities are
shown separately. An unrelated sibling wait does not suppress current work.

An observed `state_matches` predicate is a business result, not whole-task
completion. Recovery retains delivery, descendants, waits and explicit proof
obligations. Missing source or unsupported semantics remains unknown; it is
not evidence that the business action was never performed. Default tools do
not acquire new approval, rebind or bookkeeping requirements.

## Commentary capability decision

The local Codex 0.153.4 generated app-server schema has `agentMessage` item
identities and an optional `phase`; its description explicitly allows unknown
phase. Native desktop transcript samples also contain completed AgentMessage
records with message identity, thread, turn, commentary phase and completion
time. Therefore **message observation is available in the inspected host**;
it must not be described as a missing message channel.

A bounded association is technically feasible without an explicit question ID:
a validated message thread/turn can select the unique immutable human root and
its information spans. Multiple roots in a steered turn, incomplete history or
conflicting message identity must stay unknown. The existing final-reply
association is a useful source model, not a completeness oracle.

PreCompact and SessionStart already have transcript-reading paths. The current
terminal adapter requires a tool-call identity, so it cannot simply be reused
for commentary; a versioned message reader would need its own stable snapshot,
source identity and event-watermark checks. Actual pre-compaction visibility
and ordering are still native evidence gaps, not proof of impossibility.

Those records do not establish which root question the content fully answers,
whether a partial answer became complete, or an independently acknowledged UI
delivery. A completed message is not automatically a completed answer.
[Official Hook documentation](https://learn.chatgpt.com/docs/hooks) also
states that the transcript format is not a stable Hook interface. The sampled
wire is version-specific evidence, not a portable guarantee.

A finite answer validator could certify an independently specified expected
answer (for example an exact requested field against a Host fact), but the
current free-form explanation/tutorial contract supplies no such completeness
oracle. A two-topic question answered for only one topic can have the same
no-promise/no-action diagnostic shape as a full answer. Reusing final-answer
heuristics would therefore close partial commentary. Message-completion flags,
model declarations and silence before a tool call cannot resolve that gap.
A supported semantic route needs independently validated answer coverage or a
trusted user acknowledgement associated with the question and message; an
additional message-ID field alone is insufficient.

The `commentary-observation/v1` snapshot uses the separate
`codex-transcript-item-completed/v1` source. It streams a stable whole transcript up to 512 MiB, retaining at most one
2 MiB line and 8,192 message identities. The displayed snapshot contains at
most 512 messages with exact total/omitted counts; omitted identities still
participate in conflict detection. A private integrity anchor verifies the
previous byte prefix on later reads. Truncation, replacement, changed prefixes,
concurrent writes, conflicts or unsupported inputs yield unknown; the anchor
survives an unknown result without becoming message or answer evidence.
Identical messages are idempotent; different IDs retain separate observations,
including corrections.
A wrong session, child-agent source or conflicting ID cannot become a root
answer. Null phase and old roots without immutable turn bindings remain unknown.
Only hashes and bounded identities are saved in the private session sidecar;
no reply prose is copied. Recovery, status and diagnosis display recorded
counts and snapshot freshness. A changed source is labeled as a recorded
snapshot, not re-certified as current; status revision includes this view.
No answer-coverage oracle is adopted by this feature.

### Zero-model batch input contract

Run `python tools/validation/batch_preflight.py MANIFEST --output NEW_RESULT`.
The versioned `native_acceptance.py` entrypoint also accepts
`--batch-manifest MANIFEST`, validates the manifest and actual runtime digest
before executing acceptance, and rejects a mismatched source identity.
`--preflight` still performs no installation or model acceptance.

`execution_probe.py --cwd EXPECTED_CWD --fixture FIXTURE --witness INPUT
--output NEW_RESULT` exercises the invoking process's temporary write/read/remove
and Git object access. Invoke it through the intended restricted route. It
never infers another process's permissions, PowerShell language mode or Hook trust.

`acceptance_evidence.py --input REQUEST --output NEW_RESULT` supports
`evidence_index` and `transfer_readback` operations. The latter hashes the actual
receiver files and compares their inventory with the claimed stages; a receipt
can remain unknown even when its JSON was successfully written. Neither CLI
performs a transfer, login or model call, and existing result files are preserved.

Both files belong outside the source checkout. Existing result files are never
overwritten. The `cg-native-batch/v1` manifest supplies:

- Full `source_commit`, `runtime_tree_sha256`, and authoritative `plan_sha256`.
- `fixtures`: local `repo`, existing `initial_head`, and nonempty unique
  repository-relative `changed_paths`.
- `sessions`: distinct identities with `git_trust` and `continuity` roles.
- `inputs`: exact `path` and `sha256` for the planned `hook_capture`,
  `git_witness`, `continuity_witness`, `cleanup_witness`, and `oracle` input
  roles. These can be reviewed driver/input definitions for a future batch;
  they do not become evidence that those future events occurred.
- `expectations`: original `contract` anchor, `kind=current_contract` and
  `assertion`; unsupported additional expectations require a scope decision.
- `budget`: positive integer `turns`, `turn_seconds`, `startup`, `compact`,
  `cleanup`; `driver_timeouts` must equal the derived inner-turn, outer-run and
  outer-resume values. The tool checks declared settings; an unmodified private
  driver has not thereby adopted them.
- `permission_route`: `same_restricted_route` or `unavailable`. Both retain
  effective-child permission as unknown until a real equivalent-route probe.

`inputs_ready` means static inputs passed. It does not permit model execution
when required capability or native gates are missing. Use the versioned native
entrypoint's own `--preflight` with the final arguments as well.
