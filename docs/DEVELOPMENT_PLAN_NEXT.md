## 1. 交付范围和责任

开发执行者负责完整源码审查、实现、回归、性能测量、历史库逐案执行、候选文档和开发环境隔离安装，交回可独立验证的候选。协调者负责接收后的独立复核、有限返修、macOS/Windows 原生验收协调和后续发布。开发交回不是终点，也不能把未跑的平台或历史案例改成通过。

产品实现唯一上游是本仓库。历史库是配套验收输入，不是第二份产品实现。DSH 参考工作仅提供失败模式：只有本仓库复现或共享契约差异才进入修复；不复制它的锁协议、实现或验收结论。共享 core、conformance 或 consumer pin 真正改变时才触发对应下游检查。

## 3. GPT-6 适配设计

### 3.1 根据官方建议做减法，保持与模型名称无关

官方建议强调精确的 Skill 触发条件、按需读取、明确任务完成条件，并提醒 GPT-6 Astra 可能过度遵循旧的停工或重复测试指令。依据是 [Using GPT-6](https://developers.openai.com/api/docs/guides/latest-model) 和 [Rethinking skills and prompts](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)，读取日期 2026-10-02。这些是调整依据，不是本产品在所有 GPT-6 模型上通过的证据。

采用同一套简洁的默认契约，先评估 GPT-6 Astra、GPT-6.1 Sol 和 GPT-6 Luna。模型 ID、推理强度、宿主版本由实际模型批次记录；不在 Hook 内按模型名称降低门槛，也不改变用户的全局模型配置。不假定 API 模型名等于宿主可用别名。

### 3.2 四个指令面分别处理

| 指令面 | 设计与验收 |
| --- | --- |
| Skill description | 改为短而准确的启用条件；删除“任何需要正确性都使用”类过宽触发。显式启用、长任务/恢复及确需私有证据审查的入口仍可发现。 |
| Skill 根文件 | 保留职责、普通完成、失败/未知、恢复约束和少量条件路由；将发布、独立回答审查、导出、高级 proof 和完整命令移至已有 references。默认任务不能为了了解可选流程读全套文件。 |
| 动态 Hook 注入 | 普通回合注入当前事实、必要不变量、完整范围的发现入口；高级私有命令按需发现。每个 turn 更新合法绑定，不能重用过期控制。 |
| 仓库 AGENTS/开发流程 | 只精简本仓库 project-doc 中重复规则；保留权威契约和按变化类型读取的路由。受管理的全局/GitHub/macOS 区块不得在此改写；需要上游调整时单独交回。 |

每个删去或外移的规则应在简短映射中标注：仍由哪个代码检查、规范或条件引用承接。删除重复指导不等于删除断言；不要把整个旧 Skill 换名放入每次必读的 reference。

### 3.3 普通路径与高级路径

当前 `completion_command_context` 在每个活跃回合生成 status、checkpoint、disposition、proof 四条带完整绑定的命令。改为一个短的、当前 turn 可用的发现入口，优先复用 `checkpoint-status`；执行者先验证现有命令能否提供全部高级命令，必要时添加只读详细输出。不得通过读取原始 state 文件或公开 token 来补齐发现能力。

普通任务无需主动调用这个入口；自动完成沿用已有证据绑定。只有显式高级 proof、歧义证据、人工选择或排错才读取详细契约。跨平台 shell quoting、长路径、中文路径、空白和 shell 元字符均要验证。turn 变更、resume/compact 后提供新绑定，旧绑定仍被拒绝。status/diagnose 的默认输出不得新增秘密。

恢复内容分配优先级为：当前必需义务与祖先约束、未解决等待及纠正、证据状态和分页入口、按需操作提示。不能再因四条重复命令先占满预算而挤掉需求。保持完整行打包、遗漏数、投影身份和可靠分页；从小预算页面能找回全部必需项，不能把被截断内容理解为不存在。条件路由失败时保留安全且可执行的诊断，不能要求用户手工猜命令。

### 3.4 模型验证的边界

确定性检查保证内容覆盖、长度、绑定、分页和功能；真实模型小批次检查是否少读无关文件、少做多余 status/checkpoint、少重复测试、保持持续完成。把纯问答、改文件并测试、侧问后继续、合法外部等待、压缩后恢复、显式视觉 proof、采用的 release 合约分开。高级路径不得因短 Skill 而不可达。

API token 用量、宿主 usage、字符/字节代理值分别报告。缺少 tokenizer 或 usage 时不能把字符数称为 token。模型缺席只能缩小模型兼容声明；不能伪造覆盖或降低确定性门槛。

## 4. 全流程性能设计

### 4.1 首先测生产入口

调用链为 Hook 定义 → shell/PowerShell → Python 路由 → 必要的状态核心 → 锁/加载/验证 → 事件处理 → 保存/恢复。现有 `benchmark_stop --mode process` 从 `context_guard.py hook` 开始，不含全部 launcher/router 成本。因此本版增加实际 Hook command 的父进程计时，保留核心、全入口和真实宿主三种不同口径。

覆盖九个事件、冷启动、状态增长、锁竞争、错误及退出。记录 Python 进程数、文件读写/摘要次数、projection/parse 次数、注入量、RSS/峰值与整条任务耗时。setup/clone 不混进稳态测量，但另报 setup 成本。失败和 timeout 计入结果，不挑最快一次。

### 4.2 路由和启动

优先减少一次多余 Python 启动：可将 heavy fallback 改为同进程惰性调用；若 `-S`/导入、异常、exit 或 Windows 语义无法证明等价，则使用经过验证的 exec 替换或专门事件直达。实施者需比较实际方案，选择复杂度最低且两平台正确的实现。

必须保持原始 stdin 字节、stdout JSON/stderr 分离、返回码、信号/终止和子进程清理。不要在 light path 提前 import 全部核心。候选有状态路径每次事件至多一个负责产品计算的 Python 进程；解释器能力 probe 单列，能消除重复 probe 时必须有真实路径/版本身份与安装检查，不能信任任意可执行文件名。保留调用者环境所需部分，不扩大凭据传播。

默认 PreToolUse 的 ordinary edit/test/commit/branch push 应在证明不属于 release 检查范围后直接结束；不得重复解析同一命令或读写会话状态。可抽出共享的纯分类/路由函数，但路由器不能维护一套弱化的 release 判定。显式 release、未知先前 release posture、不透明 runner 和异常输入保持原契约。不要通过缩窄 matcher 或漏掉 PostToolUse 来提速。

### 4.3 事件内投影及有界 memo

上版 `EvaluationContext` 仅在 Stop 中显式创建。本版在 profile 证明有收益后，将“单事件、单稳定阶段”的机制用于 UserPromptSubmit、PostToolUse、SessionStart/PreCompact/recovery/status 的重复纯工作。每个接入点先画出读集合、写集合、phase 边界和消费提交点；不得把 Stop context 直接穿过外部事实变化。

所有 memo 共用有界预算：原始文本、masked view、fragments、search matches、clauses、索引和值的估算均纳入；条数限制保留作第二层限制。使用保守确定性 size accounting，测试另用 tracemalloc/RSS 验证总体增长。耗尽时退出 memo、直接计算，决策和完整范围不得改变。相同内容复用不重复占账，巨大单条输入不滞留；跨事件不保留 cache。

不能缓存最终 allow/block、文件/Git/Host 现状或独立 review sidecar 结果。对 memo 返回的可变对象建立只读约定并测试调用者原地修改，必要时返回不可变结构或局部副本；不得用每次深拷贝全状态代替设计。

### 4.4 状态 I/O 和工作流成本

先确认 `load_state`、完整性检查、root control、transcript 解析、原子保存和 cleanup 的实际成本，再做窄改动。只允许跳过确证不改变语义或持久性义务的写入。PreCompact 的 pending/ready、SessionStart 的 consumed、Stop 的回滚快照有崩溃恢复意义，不能机械合并两次 save。source/control/review watermark 变化必须使相关纯投影失效。

SessionEnd 具有三秒宿主时限，重点检查恢复生成和历史清理。清理不得访问当前活跃会话或以每次全库扫描制造无界尾延迟。任何 bounded cleanup 要有安全续行和所有权边界；不新增后台 daemon 或状态服务。

开发流程只在需要时加载文档、运行 owning tests；完整矩阵在已知失败家族和候选读者文档收敛后执行。一次根因修复不自动生成新正式 RC。已有相同输入证据复用，真实失败或输入变化才重跑；详见执行附录。

## 5. 正确性加固与锁子设计

### 5.1 已证实的互斥缺陷必须先关门

`filesystem_session_lock` 以 mtime 超过 30 秒为由删除锁，而且 finally 无条件按路径删除。活进程被暂停、慢 I/O 或时钟变化时可失去锁；旧 owner 退出还能删除后来 owner 的文件。此次独立合成反例已观察到两个真实进程同时处于临界区。不能通过缩短 Hook 运算、延长 stale 时间或多加一次 stat 声称修复。

WP-01 应交付小型锁决策记录：原语、线性化点、持有者身份、退出/崩溃行为、未知状态、旧版本共同访问及回退。在锁家族测试通过之前，不冻结运行制品。

推荐先验证标准库提供的内核锁方案：Unix 的 `fcntl.flock`、Windows 的 `msvcrt.locking`，使用稳定锁文件和非阻塞获取加 monotonic deadline，持有 descriptor 覆盖整个状态事务，不 unlink 正在被其他 descriptor 使用的文件，不把 PID/年龄当租约。Python 官方 API 见 [fcntl](https://docs.python.org/3/library/fcntl.html) 与 [msvcrt](https://docs.python.org/3/library/msvcrt.html)。这些 API 的存在不证明当前方案已跨平台通过；还要验证 Windows 锁字节位置、初始化、关闭/子进程继承和实际本地文件系统行为。

**旧版互操作是先决条件。** 旧 O_EXCL writer 不认识新内核锁；只换一个锁文件名、双重锁或写一个旧版不读取的 marker 都不能证明互斥。不得自动把新旧进程引到同一可写会话树。优先保持旧任务绑定其原缓存和原状态，新协议只用于隔离的新状态命名空间；需要恢复旧会话时，必须有真实停写/独占证明及不可变源快照，再迁入独立目标，防止两个历史分支被当成同一连续任务。若宿主无法保证绑定或静止条件，保留旧路径并明确阻断该迁移，不能初始化空状态掩盖旧任务。

上述隔离方案可能改变安装/恢复契约，必须先由协调者审查可执行的升级路径、回滚及版本选择，不能仅凭本段直接实现数据目录切换。允许实现者提出保留现有存储的更小方案，但须用同样的旧/新双向并发、崩溃和恢复证据证明，不以经验判断替代。常规函数命名、代码拆分和测试组织无需反复确认。

锁错误只约束需要写私有状态的路径，不得重新阻止默认普通工具。没有可靠 ownership 时，状态事务 fail closed；活 writer 不得被接管，新协议自身的崩溃也不能留下永久不可恢复的空 owner。网络文件系统/多主机共享 HOME 未证实则明确不支持，不扩张为分布式锁项目。

### 5.2 完整审查按边界收敛

开发者必须覆盖[审查基线的模块表](NEXT_REVIEW_BASELINE.md#3-完整源码审查地图)，每一行交回 inspected 路径、结论、测试及待办；“没有修改”也是有证据的结论。源码文本检查、动态反例和原生观察分别标注。至少审查：

- UserPromptSubmit 来源/控制提取、supersession、独立任务与同任务续行。
- PreToolUse 默认旁路及显式 release；PostToolUse 成功/失败/缺失终态与复合命令。
- Stop 信息交付、执行结果、proof、Goal、等待、纠正预算和失败回滚。
- 原始 UTF-8 span、路径/符号链接、大小写/Unicode、同时间戳与重复事件。
- 恢复/分页、根目录完整性、受控外部依赖、子任务身份与父任务闭合。
- reviewer 的采用条件、来源/MAC/身份、超时/取消/一次调用及 receipt 失效。
- installer/archive 的不可变性、未知文件、并发和失败恢复；实际安装与源码分开。
- 测试 oracle、覆盖回执、candidate 身份、CI 选择和隐私扫描是否会假通过。

新缺陷用稳定编号，包含实际违反的不变量、最小反例、影响路径和退出标准。性能点没有证据时为 hypothesis，不写成已确认 bug。第二个同族反例出现后补齐状态矩阵集中修复，保留未受影响证据；不要反复执行全矩阵换取“看起来更稳”。

## 6. 历史库的硬性发布门槛

发布前，权威历史库中所有**材料完整且适用于当前产品/契约**的案例及要求的平台证据必须通过。唯一允许排除的是经逐案审查确认材料不完整、不能重建原义或执行输入的案例；排除不计为通过，也不是把失败改名。

必须从实施入口的真实 registry、legacy lineage 和 supersession 生成全量快照，冻结逐文件摘要；候选准备发布前再次比较增量。原始记录数、活动数、已取代数、完整数、不完整数、适用数、已执行数分别报告。每个 ID 必须出现在逐案表；不能只检查上版公共 fixture 或历史总数。

每条活动案例至少记录：原预期、当前契约映射、材料完整性、Codex/DSH 适用性、正负/对抗测试、源码 subject、macOS/Windows 证据层级、最终裁定、缺口及负责者。旧授权契约要映射到当前 default/release 分层，不能为了历史测试重引入默认阻止。

DSH 专属案例仍需逐案解释适用性；共享语义在 Codex 中有对应义务就执行对应断言，标注 `analogue_only`，不冒充 DSH 已通过。无 Codex 对应义务者是经审查的 `not_applicable`，不是材料不完整。历史平台 unknown 不自动免除可移植/适用平台回归。任何 required 的 failed/pending/unknown/skip/xfail/零收集均阻止发布。

`excluded_incomplete` 需要稳定 ID、缺失什么、查过哪些可用来源、为何无法构造忠实 oracle、替代合成测试边界和协调者复核。不能仅从标题含“不完整”得出例外；原始现场缺失但脱敏触发/预期足以重放时仍应执行。不能因机器不可用、测试慢、版本不匹配或暂未编写测试使用此例外。排除清单绑定冻结输入并在回交时一次性审查，不让用户反复批准已授权的同类排除。

历史 `archive-045` 只列为需要核查的材料缺口，不能直接继承另一产品或上次发布的豁免。所有回执验证真实测试节点、进程成功、setup/teardown 和实际断言；表中的 pass 字符串不等于运行通过。

## 7. 验收和设计变更规则

量化指标、测试矩阵和发布职责见[执行附录](NEXT_EXECUTION.md)。硬性不变量、反例、材料完整性与身份绑定先于性能目标。收益不足不能静默降低正确性门槛；需要调整数值目标时先提交同机基线和可解释的数据，由协调者在正式性能批次前决定。

本设计采用固定审查维度：authority、identity、state/effect/readback、canonicalization、platform feasibility、migration/versioning、verification/release boundary。P1 为可复现正确性矛盾、不可实施规范或确定互操作错误；P2 为范围内非阻断质量问题；范围外改良记 backlog。设计交接通过不表示已解决产品 P1；锁子设计和候选仍有各自门槛。

后续新证据只重开受影响维度。不得以“再全面看一遍”为每次回交自动加一轮不设边界的审查；已经要求的整仓审查仍须完整交回。最终完成条件是独立复核、历史库、双平台、精确提交 CI/HOL、发布及公开读回闭合，不能在实现或测试首次通过时停止。
